# QA preparation field ownership

The provider draft is separate from the version 1 persisted verification contract. A provider proposes `checks`, `coverage`, `baseline`, `preparationEvidence`, and `unresolved`; it cites existing files and locations but does not calculate hashes or provide operation identifiers. The host retains the raw response as a provider receipt.

The host owns the contract and work identities, revision and predecessor, creation time, admitted inputs, approved requirements, and planner-selected depth. It reconstructs those fields from the frozen candidate and inventory. It assigns stable check identities and binds observations and investigation evidence to the actual provider session and operation. It hashes referenced files inside the workspace and rejects missing, inaccessible, or escaping references. A digest confirms bytes, not that the provider actually inspected them. Source freshness is checked before publication.

Provider checks and coverage are proposals, not scope authority. The existing structural validation, independent semantic assessment and, for exceptional depth, independent challenge remain mandatory. Risk escalation goes to the planner; a provider cannot lower or revise the approved depth or author a waiver.

Older complete-candidate responses are supported: their host-owned fields are not published as authority. Identity, selected/minimum depth, policy, risk details, and input identity and digest must agree; an input reference may use a relative suffix for the same absolute path. Only missing Markdown code ticks are tolerated in specific depth-description fields; substantive description changes and changed risk references remain blocked. Requirement copies are replaced with the frozen requirement records and coverage is checked against those records. Unknown or duplicate requirement identities are rejected. This compatibility does not migrate or rewrite historical contracts.

If the provider explicitly reports a blocker rather than returning a draft, Rafi reports it without asking a format-only agent to invent a draft. Formatting repair is bounded and cannot provide new investigation evidence; the original investigation remains the evidence source. Absolute working directories are usable only when they were safely mapped from the original disposable snapshot.

## Investigation notes

QA and Builder rule documents and each enabled skill currently enter the inventory as a single mandatory requirement containing the entire document. This preserves the existing authority, but can make drafts and independent assessments large and costly. Splitting or classifying those documents needs a separately verified mapping that preserves every enforceable obligation; this change does not silently remove or weaken them.

The host's existing prerequisite preflight detects host executable availability and records limited read-only probes. Host availability is not proof that a confined provider can execute a tool. No shell, network, or write permissions were broadened. A `preimplementation` check means readiness established before Builder starts, not a test-first step the Builder must perform later. Such later steps need verification of the recorded sequence rather than a fabricated passed baseline.

## Disposable rollback rehearsal update

Rafi now offers `rafi qa-rehearse-rollback` for npm projects. It captures the uncommitted product state in an independent temporary Git repository, tests it, reverts a synthetic commit, tests the restored state, and verifies the tracked files match the captured HEAD baseline. This is not proof that an individual ticket or an already existing implementation commit can be reverted: the synthetic commit includes all uncommitted product changes. It rejects symlinks and does not install or link dependencies. The project test script still runs with the calling sandbox's permissions.

The Builder can invoke only the fixed rehearsal operation, bound to the Rafi executable that launched the build; this does not grant general copy or Git-revert commands. Real Claude and Codex Builder sessions both ran it successfully on the previously failing arithmetic fixture: six tests passed before rollback and the baseline test passed afterward. A first full Claude retry still stopped during independent QA because its assessor did not recognize the baseline comparison or regard the synthetic commit as equivalent to the approved rollback procedure. The QA guidance has since been clarified without waiving requirements, and another full live run is in progress. A resumed run also exposed a preparation-failure telemetry ID collision; the retry now reports an exhausted allowance instead of hiding it behind a telemetry conflict.

The subsequent full Codex journey reached the Builder, and the rehearsal passed, but independent final QA rejected the result because the historical test-first and rollback output was not available in the review context. The diagnostic database did retain bounded provider observations, but the review did not receive them. Metadata-only observations are now projected to the reviewer for the relevant run and ticket, with explicit caveats: they are not proof of historical source state, command behavior, or an independently verified test result. Command text is not sent through this projection. Because output excerpts can contain sensitive project data, they are excluded by default; the user authorized including bounded excerpts for the current live test. The first test used `RAFI_QA_COMMAND_OUTPUT_EXCERPTS=1`; the current opt-in instead requires the exact ticket ID, e.g. `RAFI_QA_COMMAND_OUTPUT_EXCERPTS=T001`, to avoid authorizing other tickets. Excerpts are provider-reported, may be truncated, and do not prove the historical source state. Preparation guidance also distinguishes a required passing baseline from a newly invented failing test-first phase; explicitly required sequences remain requirements. Further fresh live runs are needed to establish whether the evidence is sufficient for final QA; do not treat a passing rehearsal alone as an end-to-end pass.
