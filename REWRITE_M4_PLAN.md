## 5. Order of work

A scenario or step that passes on its first run is never counted as test-first: for each of its expectation bullets, run at least one mutation that removes the behavior and save it as `.rafi-build/M4-red/mutation-<scenario>.log`; a mutation that doesn't fail the step means the test is vacuous: harden it and show the mutation failing. Large output goes under `/private/tmp` and is searched, not printed.

## 9. Risks, and what can only be checked live

No paid model turn is planned. These stay **unverified** until an authorized live run, or CI:

1. **Real providers after rafi's SIGKILL.** Whether a real `codex app-server` and a real `claude` stop when their stdin closes mid-turn, or finish the turn and keep editing the project while the redo runs. The fakes exit (item 11). A free partial probe is possible (start `codex app-server`, close stdin before any turn, see it exit; skipped without `codex`); mid-turn needs a paid turn.
2. **Real Ctrl+C in a terminal** sends SIGINT to the whole foreground process group, providers included. How real Codex and Claude react (exit before rafi's cancel, or ignore it) decides whether OUT-14's "waits for the provider to take the cancel" holds; the fakes are scripted to take the cancel. Live only.
3. **Cancel confirmation on real Codex** (`turn/interrupt`): M2's live check confirmed Claude's (35 ms, `REWRITE_M2_PLAN.md:471`); Codex's should be re-checked in the next authorized live run.
4. **Linux and Windows** (CI after a push): `/proc` start times, `--detach` with `setsid` and on Windows, `ps` and `lsof` in the process set, `PRAGMA data_version` polling.
5. **Budgets.** `build/` about 1,930/2,000 and `api/` about 560/600 after M4 (2.5), before M5's delivery and M5–M9's actions; `deps/` over without P36.
6. **The fast suite's ceiling.** It's bound by total work (0.1). M4 fits only with slice 0 and P33; M5 (git boundaries) and M6 (questions) add enumeration points (ARCH 14.1), so M5's plan will need its own room, for example grouping unit tests into fewer jobs or a second structural cut.
7. **P33's snapshots.** The database copy is consistent (C163). But the project's byte copy can catch a file write still in flight at the hook. That's a valid crash state, but it can vary between runs. A failure that shows up only sometimes is a real bug, and the report says which point and snapshot showed it.
8. **S-QA-4 (b)'s reading.** SCN's `crash` is the provider exiting mid-turn, which rafi retries inside the run, so its `rafi resume` finds nothing; C148 also runs the rafi-crash reading so both are covered. If you meant only one, the other is dropped.

## Questions for the user

**1. How should the fake `codex` and `claude` programs tell which ticket a turn is for? (P8, P35)**
Rafi's real transport drops the turn's identity, and the scenarios forbid reading it from prompt text. M4's real-kill and real-Ctrl+C runs need it, and so do later process rows.
- **A. Guess from the reply type and the order of turns.** Nothing new is built except a counter in each fake. But a turn redone after a kill shifts the order. So S-CRASH-1's kill sample would have to use the plain happy-path script, and the scenarios' "match by ticket and attempt" rule can't hold.
- **B. Put a fixed line in every message, `rafi-turn: T2 review attempt 1`.** Built: the line, a parser in each fake, and a test that it matches. But every real agent sees it, M10's prompt rewrite must keep it, and it breaks "nothing is read from prompt text".
- **C. The fakes read it from rafi's own log (recommended).** Built: `turn.intent` gains `ticket`, `step` and `attempt` (v 2); a small reader in the fakes; a test that it always matches what the in-process fake sees; `better-sqlite3` as a test dependency.
- **Recommendation: C.** Agents and users see no change, one script works in both modes, and a redone turn keeps its identity, which the kill sample needs. The cost is that a test fake reads rafi's database, for matching only. At capture level `none` (M9) it falls back to order.

**2. What should Ctrl+C do in a second terminal that's watching a build through `rafi resume`?**
- **Detach (recommended):** the build keeps running, and the view says "`rafi stop` stops it." Reason: a viewer shouldn't stop a build by accident, and `rafi stop` exists for that.
- **Stop:** the same as Ctrl+C in the build's own terminal.
Until you answer: detach.

**3. What should `rafi start` do when the last build is unfinished but nothing is running it** (it crashed, was stopped, failed, or finished with work left)?
- **a. Start the new build (recommended).** It first redoes any interrupted step, and the old build is marked superseded. Reason: no extra step after a crash or a stop when you want a new scope.
- **b. Refuse,** pointing to `rafi resume` or `rafi reset`. Nothing is ever superseded, but it costs an extra command.
- **c. Ask in a terminal** (continue, start new, cancel), and refuse without one.
Until you answer: a.
