### 3.4 Race tests (check-then-act)

M4's review found check-then-act races (`REWRITE_M4_PLAN.md:572-582`). Every M5 command or step that checks state and then writes, or touches git, decides inside the write transaction (`BEGIN IMMEDIATE`, as `engine.own(…, { since })` and `writeSince` do) and gets a deterministic race test that forces the interleaving with the harness's `busyAt`, `onGit`, `pauseAt` or `whenTimer` (as `race-m4.test.ts` does). **Git and PR effects (R11–R16).** A git ref or a pull request can't share a transaction with the log, so each effect is decided in three parts (C235): a lookup; a guarded write of `git.intent` with what the effect should leave (P51), in which the owner, the delivery definitions' digest (R19) and the lookup's answer are checked; then the effect itself, made with git's or the provider's own compare-and-set, so a competitor that lands between the lookup and the effect makes the effect fail instead of doubling it. After a failure or a crash, rafi looks again for exactly the intent's result and records it, adopts an equal result someone else made, or stops with the category of C201. Rafi's own competitors are kept out by the lease (R9); these rows force the outside ones (you, another clone, the provider, a CI bot) at each lookup→act boundary. Each row asserts exactly one of each result (commit, ref update, PR, merge) and one result event, and its mutation removes the compare-and-set (plain `git commit`, `update-ref` without the old value, a PR created without the "already exists" handling).

**M5's own design keeps its cost down:**

- `gh`, `glab` and `fetch` are in-process fakes in the fast suite (no process start); the executables run only in the process set (C216).
- Delivery fixtures (F-BRANCH, F-DIRTY) have QA off (`harness.qa: false`), as C159 did for F-BIG34, except where a scenario tests QA (S-QA-5's clause). SCN gives neither fixture a QA rule.
- Builds use the smallest scope SCN allows; worktrees are removed only where `keep_worktrees` isn't the point; `push` (70 ms) only where completion needs it.
- The git enumeration uses P33's forks (one ticket fully, the other at its first and last git boundary, as C227 and P45 read ARCH 14.1) and two literal points.
- C235's intents are one guarded write each (about a millisecond), not a git call; C236's `write-tree` plus `commit-tree` plus `update-ref` replaces `git commit` (one more child process per ticket, about 10 ms, measured in slice 5).
- No job over 10 s: S-BATCH-2 is three shards; the enumeration two if needed.

**Checkpoints:** three runs at the end of slices 0, 4, 6, 8, 10 and 13; the slowest is reported, with job time and load average. **Under 50 s:** carry on. **50–55 s:** apply the next measured mitigation from the profile before the next slice, and report it. **55 s or more** (slowest of three): stop and report before adding more, with the profile, what's been tried, and the options, none of which drops required scope without the user's approval. **60 s or more:** the gate fails; nothing is merged.

**What belongs in the process set** (real processes and real time, never the gate): the `gh`/`glab` executables (item 20), the SIGKILL during a real `git push` (item 21), the Codex profile probe (item 22), the handler-versus-executable fidelity check (item 35), and S-START-5 step 4's `--detach` (already there). ## Questions for the user

Short answers are enough. Each says what's built under each answer; until you answer, the recommended option is built (section 1), and every choice here is reversible.

**1. Should rafi's own git commands run your repository's hooks?** An agent can edit hook scripts in its worktree (`.husky/`, or any folder `core.hooksPath` names), and rafi runs git outside the agents' sandbox with its full environment.
- **a. Never (recommended).** Reason: otherwise an agent can run code outside its sandbox. Built: rafi's git calls get an empty hooks folder and `--no-verify` (C197); your own commits still run your hooks.
- **b. Run them inside the test sandbox.** Built: hooks run sandboxed with the test environment; slower, and hooks that need the network or your home folder fail.
- **c. As today.** Built: hooks run normally.

**2. A file rafi is about to commit contains a declared secret value. What then?** (A test can write one into a report file that isn't ignored.)
- **a. Hold that ticket's commit (recommended).** Reason: nothing secret ever reaches git, and only that ticket waits. Built: nothing committed; one line names the file and the variable, never the value; the ticket is blocked (a legal step failure today, no doc change); you delete or ignore the file, then `rafi tickets unblock <id>` and `rafi resume` (from M6, "I fixed it myself"); rafi scans again and commits (C236, R17).
- **b. Commit everything except that file, and say so.** Built: the file is left out of the commit and stays in the worktree; the build goes on.
- **c. Commit it anyway, with a warning.**

**3. Should each ticket's commit carry rafi's progress files (`.rafi/progress.yaml`, `docs/ticket-progress.md`) when tickets get their own branches or PRs?**
- **a. Yes, as the docs say (recommended).** Reason: it's the locked contract (ARCH 3.7 `:412`, 3.8 `:423`), and a clone always gets the progress. Built: the files ride on every rafi commit; while the build runs, rafi keeps its PRs mergeable by resolving conflicts in these two files itself (C240). Cost: a PR you merge after the build may show a conflict in them; either side is fine, rafi fixes the file on its next run.
- **b. Only commits on the base.** Built: ticket and stack branches don't carry them; only a `direct-merge` commits them; with PR completions they stay in your working tree to commit. Needs doc change P52.

**4. How should "Builder resolves the conflict" work when a delivery merge conflicts?** The unit's tickets are already done, and done tickets are never reopened.
- **a. A rafi fix ticket for that unit (recommended).** Reason: it fixes forward like CI fix tickets and keeps one branch and one PR. Built: rafi starts the merge in the unit's worktree, the builder resolves the files, it's checked and reviewed, rafi commits it and retries the unit's delivery (C237, P50 a).
- **b. Drop it for 1.0.** Built: the question offers "I resolved it myself (retry the merge)", "Skip this merge" and "Stop the build" (P50 b).

**5. Approve the doc changes P40–P51?** (P50 follows question 4; P52 only if you answer b to question 3.) Exact text in 8.1. **Recommendation: approve all.** Reason: P48 stops an agent changing rafi's own settings; P41 and P51 keep a change or a git action from being recorded or done twice; P47 keeps a tracker token off other hosts; P49 keeps a fix ticket on a clone; the rest fix scenario text that can't be built as written.
