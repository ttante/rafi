# Guide: restarting a pre-0.10 project's build on Rafi 0.10

Worked example: MoneyTree (`/Users/tyler/reps/activeWork/moneyTree`), 2026-10-25.
The tickets were generated by an older Rafi, the builds never worked, and the
goal was a clean 4-step build on the 0.10.0 comms rewrite. Steps are in the
order they were done. Each pitfall gives the symptom, the cause, and the fix.

## 0. Use the Node version Rafi was installed with

The shell defaulted to Node 18, but the global `@rafi-ai/cli` 0.10.0 lives
under Node 24 (`.nvmrc` in this repo says 24).

```sh
export PATH="$HOME/.nvm/versions/node/v24.21.0/bin:$PATH"
node -v && rafi --version     # v24.x, 0.10.0
```

Symptom on the wrong Node: `SyntaxError: ... 'node:fs' does not provide an
export named 'statfsSync'`. When building the rafi workspace itself, rebuild
the native module after switching Node versions
(`npm rebuild better-sqlite3 --build-from-source` in the repo root). Symptom:
`NODE_MODULE_VERSION 115 ... requires 137`.

## 1. Inspect before touching anything

```sh
cd <project>
git status; git log --oneline
rafi doctor .
rafi status .          # "v2-cutover-pending" = the DB was written by Rafi <0.10
rafi tickets queue
```

Find out which files old builds produced. Compare file timestamps with the
ticket population time (`.foreman/*-tickets-populate.jsonl`) and with
`.rafi/install-manifest.json`, which records every file Rafi itself created,
along with its sha256.

## 2. Reset the source to the post-ticket state

- Move build-only output out of the repo. Don't delete it until you're sure.
  For MoneyTree that was `packages/`, `tests/`, `CHANGELOG.md`,
  `docs/starnet-integration-assessment.md` and
  `docs/decisions/0001-starnet-adapter-boundary.md`.
- Rafi scaffold docs that a build edited can be restored byte-exact from
  `packages/special-agents/content/docs/<file>`. Check the result against the
  manifest's `installedSha256`.
- Leave `.tickets/` alone.
- Commit the baseline so the build and QA start from a clean `HEAD`.
  Keep nested reference repos (e.g. `rafi-ref/`) and local archives out of git
  with `.git/info/exclude`.

## 3. Reset Rafi's execution state: `rafi build:reset . --yes`

This archives `.rafi/recovery.sqlite3` and `.foreman/runs/*.json` under
`.rafi/recovery-archive/<timestamp>/` and resets every ticket to planned
(34 for MoneyTree). Source files and logs are left alone.

**Pitfall (fixed on branch `fix/build-reset-legacy-recovery-db`):** on 0.10.0
the reset fails immediately with

```
Build mutation rejected: original admission authority is stale or missing
```

Cause: `build:reset` opened the old database through `WorkflowDb`, and that
runs the v2 structured-communication cutover first. The old DB still held the
build admission of a dead Oct-22 worker. The cutover's writes (continuity
events, purging fenced runs) are rejected by the build-fence triggers because
the caller doesn't hold that admission. So a legacy project with a crashed
build could not be reset, started, or inspected at all.

Fix: `build:reset` now reads owners (build admission, project lease, running
supervisors, owned processes) through a read-only, migration-free connection
(`ai-foreman/recovery-owners.js`). It refuses if any owner is alive or
can't be verified, and otherwise archives the DB untouched. The fresh DB
created afterwards completes the cutover normally. Regression test:
`packages/rafi/test/buildReset.test.ts`.

Until a release contains the fixes from branch
`fix/build-reset-legacy-recovery-db`, run every Rafi command from the
workspace build. Several fixes below change the build itself, not just
reset.

```sh
cd <rafi repo>
corepack pnpm install --frozen-lockfile   # see "workspace CLI crashed natively" below
corepack pnpm build
alias rafi_ws="node <rafi repo>/packages/rafi/dist/launcher.js"
rafi_ws build:reset <project> --yes
```

## 4. Bring up the project's external prerequisites

MoneyTree's T001 (the root of every dependency chain) needs a live StarNet at
`http://localhost:8787` with a model provider. Without it, every step blocks
on T001.

1. Model: `brew install ollama`, run `ollama serve` (a session process, not a
   brew service), then `ollama pull qwen3:0.6b`. That's a tiny placeholder
   model that supports tools; this machine isn't the real local-AI box.
2. StarNet from the pinned checkout, using a known API token:
   `node sidecar/index.js` in `vendor/starnet`, with `STARNET_API_TOKEN` set.
   Otherwise the token is random per launch.
3. Write the settings to a git-ignored `<project>/.env.local`
   (`STARNET_URL`, `STARNET_API_TOKEN`/`STARNET_TOKEN`, `STARNET_PROVIDER`,
   `STARNET_MODEL`). Source it before `rafi start` so the builder inherits it.
   Also export `STARNET_ENV_FILE=<abs path>`: Codex hides `*TOKEN*` variables
   from builder shells by default, but a variable named like this one reaches
   them and points at the token file.
4. Verify one real bounded task before launching the build:
   `POST /api/run` with `provider: "ollama", model: "qwen3:0.6b", isTask: true`
   must end with `agent.run.end` and `reason: "done"`.

StarNet findings worth knowing (they're also in `.env.local`):

- `GET /api/runtime/agent` always advertises provider `openrouter` +
  `STARNET_DEFAULT_MODEL`. Pointing `OPENROUTER_BASE` at Ollama makes it
  report `configured: true`, but tasks on that pair are refused ("does not
  support tool calls"). The openrouter catalog then comes from Ollama's
  `/v1/models`, which carries no tool metadata.
- `provider: "ollama"` in the `/api/run` body works.

## 5. Launch the build

With the branch build, one non-interactive command runs without stopping:

```sh
cd <project>; set -a; . ./.env.local; set +a; export STARNET_ENV_FILE=$PWD/.env.local
rafi_ws start . --steps 4 --builder-network --qa-network --yes --detach
```

- `--yes` never stops to ask. It approves the plan, plan updates, and the
  capabilities you requested by flag. The log says
  `builder internet for this build approved by --yes`.
- `--qa-network` lets independent QA reach live services (StarNet on
  :8787). Without it, QA is offline and can never verify a live-runtime
  requirement. QA keeps a read-only workspace either way.
- Without `--yes`, each question is recorded and the process exits with
  code 2, with or without a terminal. Answer with
  `rafi build:decide . --run <runId> --decision <id> --choice <choice>`,
  then run `rafi resume . --run <runId>`; resume reuses that answer.

**Fixed on the branch (0.10.0 behavior):** with no terminal, the worker
recorded the question, printed "Rafi is waiting for input", and then never
exited. Evidence: run `d9c447c1-…`, worker pid 8410 idle at 1.7s CPU. The
supervisor stayed live, `resume` refused, and the `build:decide` answer was
never read. Each resume also asked a fresh network question. On 0.10.0 the
only workaround was running rafi under a pseudo-terminal
(`sleep 2000000 | script -q t.log rafi start …`) and answering from a
second shell.

Find decision and run IDs in the prompt text (`[decision <id>]`) or in
`human_decisions`. The sqlite3 CLI can't open the live WAL database
read-only, so read a copy.

## 5b. Problems that only appeared once the build ran

**"Step 1 of 4" made the builder do a quarter of a ticket (fixed on the
branch).** Preflight asked for "the next 4 ticket(s) or step(s)". In
MoneyTree only T001 is eligible (every other ticket depends on it), so
Codex split T001 into four parts. The host's "this is step 1 of 4" then
read as "inspection only". The host's QA reviews the whole ticket after
each turn, so QA failed ("no implementation or contract tests") and the
batch ended `blocked` after about 4 minutes. Evidence: `.foreman/2026-10-26T00-27-20-800Z.jsonl`
and Codex session `01a1759a-…` ("T001 only; step 1 of 4 is inspection
only"). Fix: in ticket mode, preflight lists whole tickets only, and the
turn instructions say "ticket i of up to n" and require the entire assigned
ticket (`foreman.ts` `buildPlanningTurn` / `buildPrimer` /
`buildNextStepInstruction`).

**QA could not see the vendored checkout (fixed on the branch).** QA failed
with "the vendored StarNet source is unavailable in this snapshot". The QA
snapshot linked ignored top-level folders only for repos with no commit.
MoneyTree has commits, and `vendor/` is ignored by the user's global
`~/.gitignore`, so `vendor/starnet` was missing from QA's snapshot. Fix:
committed clones also link ignored top-level folders when the clone ignores
them too (`qaSnapshot.ts` `projectDependencyTrees`).

**After a reset, runs could start but never resume (fixed on the branch).**
`rafi resume` refused with `current plan has no matching completed host
approval`. Resuming needs the completed `rafi plan` approval receipt (a
`kind='plan'` workflow run matching `docs/rafi-plan.json`). That receipt
lived in the recovery DB that `build:reset` archives. MoneyTree lost it at
the first reset on 2026-10-22. It survived only in
`.rafi/recovery-archive/2026-10-22T18-05-55-153Z/`. Fix: `build:reset`
carries the newest approval of the *current* plan forward, from the DB
being archived or from older archives. It prints `carried the current plan
approval forward`.

**The builder blocked T001 because it lacked operator inputs.** Its
blockers: StarNet "reports no available agents", the live smoke needs
`STARNET_TOKEN/MODEL/PROVIDER/AGENT_ID`, and upstream tests fail on Node
18.12.1. Fixes, all operator-side:
- `STARNET_AGENT_ID=agent` works: `/api/run` accepts it even though the
  runtime roster is empty. Run `npm run test:live` in
  `packages/starnet-adapter` as the operator to confirm it ends `completed`.
- Export the inputs in the environment you launch rafi from. A `codex exec`
  probe confirmed Codex passes all `STARNET_*` variables (including
  `STARNET_TOKEN`) to builder shells.
- Builder shells run `zsh -lc`, and macOS `path_helper` puts
  `/usr/local/bin` (system Node 18.12.1) first whatever PATH rafi passes.
  Give the builder an explicit Node 22 path (`STARNET_NODE22=…/v22.11.0/bin/node`).
- Tell the builder with a scoped Manager control, then resume:
  `rafi manager . --ask "/guide-builder <run> T001 <operator note>"`.
  The note is queued and delivered at the builder's next safe boundary
  (`/guide-qa` and `/guide-both` reach QA too). A blocked ticket also needs
  `rafi tickets unblock T001`.
  Do not rely on `rafi tickets update T001 --next-action`: it only changes
  the tracker (`docs/ticket-progress.md`), which the builder may never read.
  It worked once here by chance; a later resume went straight into a QA
  handback and the builder ignored the note.

**`--steps 4` admits only the tickets that are currently eligible.** Rafi
prints `requested --steps 4; admitting 1 ticket(s). The next delivery unit
… is not yet eligible, so it will run separately.` In a dependency chain
(T002 needs T001), one `rafi start` builds T001 only. Run `start` again for
the next ticket.

**The workspace CLI crashed natively.** `Statement::~Statement` →
`Assertion failed: (env) != nullptr` during GC. Cause: the rafi workspace's
root `node_modules` held a stale better-sqlite3 12.10.0 from an old npm
install, while the lockfile pins 13.0.3. Fix:
`corepack pnpm install --frozen-lockfile` in the rafi repo. Check with
`node -p "require('better-sqlite3/package.json').version"` from
`packages/ai-foreman`.

**`.git/info/exclude` may be a shared symlink (fixed on the branch).**
Here git's `init.templateDir` (`~/.git_template`) installs `info/exclude`
as a symlink to `~/dotfiles/git_template/info/exclude`. Rafi appended its
entries through that link, so they landed in the one shared file every new
repo inherits. Rafi now replaces such a link with a per-repo copy before
writing. Tests that `git init` temp repos must not write through it
either.

**Wrong Node or stale SQLite now fails clearly (fixed on the branch).** The
`rafi` executable is a launcher that checks Node against `engines` (24.x),
the installed better-sqlite3 version, and that the native module loads. It
then prints the cause and the fix instead of `statfsSync` errors or native
crashes. `rafi doctor` shows the same checks.

## 6. Watch the run

- `.foreman/<timestamp>.jsonl`: `preflight`, `batch-start`, per-turn
  `provider-lifecycle`, `step`, `batch-end`
- `rafi build:attach . --run <id>`: phase, supervisor pid, recovery attempts
- `docs/ticket-progress.md` / `rafi tickets queue`: ticket states

Don't treat `batch-start` as success. Check the step records, the builder's
file changes, the QA result, and run the project's tests yourself.

## MoneyTree run log (2026-10-26, branch build)

Run `25630461-…`, started with
`start . --steps 4 --builder-network --qa-network --yes --detach`:

1. No prompts. Both network grants were approved by `--yes`, preflight
   planned T001 as one whole ticket, and the batch started.
2. The builder implemented T001 as an official StarNet plugin
   (`plugins/moneystation-studio`), a loopback adapter, contract tests, and an
   ADR. It blocked only because its 25s live timeout was shorter than the
   placeholder model's ~35s per task (the operator measured this).
3. Operator: `tickets unblock` + a tracker note (latency note,
   `STARNET_LIVE_TIMEOUT_MS=180000`), then
   `resume . --run <id> --builder-network --qa-network --yes`. Resume reused
   the exact builder session and the carried-forward plan approval.
4. The builder reported T001 done. QA reached `localhost:8787` (QA network
   works) and failed it on: the 0.6B model not returning the exact
   `LIVE_SMOKE_OK` marker; upstream StarNet tests needing a writable temp
   folder in QA's read-only sandbox; and no real artifact shown in the panel.
5. The batch ended blocked on a human-only step: a real StarNet artifact
   needs an operator-placed capability and a plugin approval in StarNet
   EXTENSIONS. StarNet forbids agents from enabling plugins, so this is
   correct behavior.

Next human steps: install `plugins/moneystation-studio` into
`~/Library/Application Support/ai.skynet.harness/workspaces/plugins/`,
approve it in EXTENSIONS, place the capability, then resume. Consider a
slightly larger local model for reliable live checks.
