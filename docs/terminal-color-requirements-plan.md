## Requirements for a color system

1. **Keep ordinary prose at the terminal’s default color.** Add color to selected labels and meaningful tokens—such as Rafi/Manager headings, phase labels, statuses, identifiers, and success or warning markers—rather than tinting full output lines, model answers, or evidence bodies.
2. **Use a small, consistent semantic palette.** Define a restrained accent for Rafi/section labels, with distinct treatments for success, warning, error, and informational status. Choose colors that remain readable on both light and dark terminal themes and work at the basic ANSI color level; do not depend on truecolor, bold, or color alone to distinguish a state. Color must reinforce existing words and symbols.
3. **Centralize styling and color-mode decisions.** Both packages should use the same small presentation API so colors and policies do not drift between build activity, CLI commands, and Manager. Rafi already depends on ai-foreman, which could host that shared API.
4. **Respect output destination and user preferences.** By default, emit ANSI color only when writing to a color-capable TTY. Define and document precedence for `NO_COLOR`, `FORCE_COLOR`, `TERM=dumb`, and any CLI override, including empty or invalid values. Make the decision per output stream; a TTY on `stderr` does not imply color is appropriate on redirected `stdout`.
5. **Keep machine-readable and redirected output clean.** JSON modes, file writes, pipes, logs, and non-TTY output must not contain ANSI by default. Identify the exact Manager commands and modes with a JSON output contract and keep those responses parseable. Some Manager host commands intentionally combine JSON with prose or evidence text; preserve their established format rather than treating all `--ask` output as JSON. If forced color is allowed in non-TTY output, explicit machine-readable modes should still remain escape-free.
6. **Preserve activity rendering behavior.** Color may style selected fields in activity rows, but must not alter timestamps, status coalescing, heartbeat behavior, cursor cleanup, prompt pauses, or the existing safe newline-record default. The current default intentionally avoids assuming that every TTY-like host handles cursor control safely. [activity.ts](/Users/tyler/reps/rafi/packages/ai-foreman/src/activity.ts:222) [activity.ts](/Users/tyler/reps/rafi/packages/ai-foreman/src/activity.ts:362)
7. **Keep arbitrary content safe.** Do not style or trust control sequences embedded in model text, ticket content, paths, or evidence. Manager evidence rendering already redacts sensitive content and escapes terminal controls, but those protections do not cover every terminal-bound value: Manager writes model response text directly, and activity’s whitespace cleaning does not remove ANSI controls. Add or apply a safe rendering boundary for all untrusted terminal-bound text before styling host-owned labels and values. Preserve evidence redaction and its byte/offset contracts.
8. **Support the requested terminal environments through standard ANSI behavior.** Use Node’s stream TTY detection and a cross-platform color implementation instead of OS-specific checks. Verify behavior in Windows Terminal, WSL, macOS, and Linux terminals. Decide whether legacy Windows console hosts are in scope; unsupported, legacy, or dumb terminals should get readable plain text. Do not assume every TTY supports the same color depth.
9. **Keep interview styling compatible.** Existing `@clack/prompts` interviews should retain their prompt behavior and appearance. Shared color helpers should not override Clack’s own styling or introduce double color/reset codes.
10. **Document the policy.** Explain the color palette, environment-variable behavior, and the guarantee for redirected and machine-readable output.

## Regression risks to guard against

| Area | Possible regression | Prevention requirement |
|---|---|---|
| Manager `--ask` and host commands | ANSI escapes make JSON invalid or change its contract | Keep JSON serialization paths plain; verify representative outputs still parse as JSON |
| Manager evidence and model text | Styling or terminal controls alter untrusted content, or expose protected bytes | Style only host-owned labels; retain existing evidence redaction/control escaping and safely render model text before terminal output |
| Activity output | Color codes interfere with redraw cleanup, line comparison, or transcript rendering | Keep status semantics and cursor controls separate; check colored TTY and plain record output |
| Piped output and CI | Escape sequences pollute logs, snapshots, and scripts | Default to no color when output is not a suitable TTY; cover `NO_COLOR`, `FORCE_COLOR`, and `TERM=dumb` |
| Untrusted terminal text | Model output or event fields can contain terminal controls that interfere with styling or alter the display | Sanitize or safely render untrusted terminal-bound text before applying host-owned styles; retain evidence redaction and test control-sequence inputs |
| Color and theme support | Colors become hard to read on light/dark themes or assume 256-color/truecolor support | Use a basic ANSI palette, inspect light and dark themes, and preserve text/symbol cues without color |
| Stream selection | Color leaks to redirected output because another stream is a TTY | Decide color separately for stdout and stderr; test mixed TTY/redirected stream configurations |
| Interviews | Shared styling changes Clack prompt colors, cancellation, or input rendering | Keep Clack as the owner of interview UI and test representative interview flows |
| Windows and WSL | Platform-specific detection or unsupported cursor assumptions break display | Rely on standard ANSI styling, avoid OS checks, and test in those terminal hosts |
| Existing tests and consumers | Exact-output assertions or scripts depend on plain text | Preserve semantic text and machine output; update human-readable expectations only when the visible contract intentionally changes |

## Suggested implementation plan

1. **Settle the palette and precedence rules.** Choose a restrained semantic palette that is readable on light and dark themes and at basic ANSI color depth. Write down how `NO_COLOR`, `FORCE_COLOR`, `TERM=dumb`, output TTY state, and any CLI override interact; ensure forced color does not color machine-readable output.
2. **Add a shared color utility.** Keep it small: stream-aware enablement and a few named semantic styles. Avoid relying on an undeclared transitive dependency; add a direct dependency if a library is selected.
3. **Apply it first to shared build activity.** Style only host-owned activity labels/statuses and retry or warning markers. Preserve phase text, the transcript-safe TTY mode, non-TTY record shape, and prompt pausing.
4. **Apply it to Manager’s human interface.** Add accents to the initial summary, interactive prompt, host guidance, and human-readable status labels. Keep machine-readable output unstyled. Before styling, safely render untrusted model output and other terminal-bound content; retain the evidence redaction and terminal-control protections.
5. **Extend selectively to ordinary Rafi interactions.** Apply the same helpers to normal command summaries, success messages, warnings, errors, and previews where color improves scanning. Leave help, raw content, and data output alone unless there is a clear human-readable presentation benefit.
6. **Add regression coverage before broad rollout.** Test color enabled/disabled behavior independently for stdout and stderr under relevant environment-variable combinations. Ensure non-TTY output and each explicitly machine-readable JSON mode contain no ANSI and remain parseable. Exercise activity rendering in both modes, test hostile control sequences in model/event/evidence text, and preserve Manager evidence redaction and byte/offset contracts.
7. **Review on representative terminals and document.** Inspect light and dark themes, an interactive build, a redirected build, Manager interactive and one-shot output, and representative interview output in macOS/Linux, WSL, Windows Terminal, and any supported legacy Windows host. Then document the final palette, supported terminals, and controls.

## Audit findings

- The shared activity path and its conservative newline-record default are confirmed in the code. Existing tests protect record coalescing and verify that automatic TTY records contain no ANSI. The color implementation should preserve those properties.
- `@clack/prompts` owns interview presentation. A shared styling layer should leave its prompt lifecycle and styling behavior intact.
- Manager output is not uniformly machine-readable. Certain evidence responses are JSON, while other host commands can combine JSON with explanatory text or evidence content. Requirements and tests should name the specific JSON modes instead of assuming every `--ask` response is a JSON document.
- Evidence rendering has redaction and terminal-control escaping. Those protections are not universal across all output: Manager emits model response text directly, and the activity reporter’s `clean` helper normalizes whitespace but does not strip ANSI control sequences. Safe rendering of all untrusted terminal-bound text is a requirement to implement, not an existing guarantee.
- Windows Terminal and WSL are distinct from older Windows console hosts. The supported Windows terminal set and plain-text fallback behavior should be decided and documented; a TTY check alone does not establish ANSI or color-depth support.

This is a codebase-grounded plan and audit; no implementation changes or tests were run.
